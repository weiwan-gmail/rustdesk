# 同一被控主机上 web 端短时间大量连接 — 情况与方案

> **状态：讨论稿，未实施（discussion only）。**
> 本文只记录与 Wei Wan 的讨论结论，**不改代码、不改默认行为、不发二进制**。
> Wei 明确说：**先不实施。** 若以后动手，请按文末「建议实施顺序」，不要从「短间隔连接次数封禁」起步。

范围：本 fork 的 **v2 直连 Web 客户端**（`deploy/v2/web-direct`）。不要在 `deploy/v1_backup` 上继续开发。服务器模式（`deploy/v2/web`）有类似「多路 web 连同一被控」问题，但本文按直连路径写具体层。

## 结论

**值得限制的是：同一被控主机上同时存在的 *active* 会话数。**

**不要粗暴封禁短间隔重连。** 不稳定网络下自动重连是正常行为；把「短时间连了几次」当成滥用，会伤到真正需要重连的用户（锁屏、Wi‑Fi 抖动、笔记本休眠尤其难排查）。

要把两类现象分开处理：

| | 误开多路（accidental multi-open） | 重连风暴（reconnect storms） |
|---|---|---|
| 典型来源 | 多标签 / 多窗口 / 多桥进程 | 断线后客户端立刻再连，或旧 WS 未关完又开新的 |
| 用户意图 | 往往没有；或协作时有意多看 | 想恢复 *同一* 条会话 |
| 伤害 | 键鼠打架、带宽翻倍 | 被控短时间堆很多半死 TCP，画面/输入抖动 |
| 方向 | 限制 **同时活跃** 的控制页 / 桥 | 退避、串行替换旧连接；**不要按次数封禁** |

协作（多人看同一桌面）是 control room 的正当用例，不能用全局速率限制一刀切。

## 三层路径

直连路径是三跳，不是浏览器直连被控：

```mermaid
flowchart LR
  page["浏览器页面<br/>Flutter Web + flutter/web/js"]
  bridge["rustdesk-web-v2-direct<br/>:8081 页面 + /direct"]
  host["被控 RustDesk<br/>:21118 直接 IP 访问"]
  page -->|"ws/wss"| bridge
  bridge -->|"裸 TCP"| host
```

| 层 | 本 fork 位置 | 现在做什么 | 和「大量连接」的关系 |
|---|---|---|---|
| 1. 浏览器页 | `flutter/web/js/src/connection.ts`（`CONF.direct` 时走 IP） | 每个标签自己连；`reconnect()` 是 `close()` 再 `start(id)`，无退避 | 多开标签 = 多路会话；刷新/前进后退可能短暂双连 |
| 2. 桥 | `deploy/v2/web-direct/server` 的 `/direct` | WS→TCP 桥到目标 `IP:21118`；进程级 `bridgeSem` 最多 **32** 路过桥（防资源耗尽，不是按被控 IP） | 每个页面一条桥；两个桥进程指向同一被控会翻倍 |
| 3. 被控 | 普通客户端，开「直接 IP 访问」，默认 `:21118` | 接受直连 TCP；系统级共享输入（大家都能键鼠） | 多路都会占带宽；输入是否打架取决于有没有 `--control` |

房间（若打开）是第四条旁路：`/control` 与页面同端口，**不传画面**，只协调谁能键鼠。见 `deploy/v2/controlroom/README.md`。

## 会出现的情况

### 1. 误开多个标签 / 窗口

同一浏览器对同一 IP 开两个远程页 → 两条 `/direct` → 被控两条 TCP。

- 默认（无 `--control`）：两路都能键鼠，输入打架。
- 开了 `--control`：谁控制清楚了，但 **两条视频桥仍在**，带宽照烧。
- 房间解决的是「谁点鼠标」，不是连接数。

### 2. 不稳定网络自动重连

网络抖一下，页面 `reconnect()` 立刻再开 `/direct`。若旧 TCP 还在 TIME_WAIT / 半关闭，被控上会短时间看到一串新连接。

**按短间隔次数封禁重连是错的。** 正确方向是客户端指数退避，桥侧尽量 **替换** 旧桥而不是并行堆。

### 3. 有意的多路协作

多人看同一被控、一人控制，正是 `--control` 的用例（`deploy/v2/controlroom`）。

不要用「全站每秒只准 N 次 `/direct`」挡住这个。若以后做硬上限，应对 **误开的控制页** 下手，并给协作留出口（房间、或明确的多 viewer 配额）。

### 4. 刷新 / 前进后退

刷新或 bfcache 回来时，旧 WebSocket 可能还没收到 close，新页已经再连。表现是 **短暂双连**，通常几秒内旧的会掉。不要当成攻击；桥日志能区分「replace-old」和「真的第二路」。

### 5. 两个桥进程指向同一被控

两台机器（或同机两个 `rustdesk-web-v2-direct`）都去连 `192.168.1.50:21118`，比多标签更重：

- 浏览器侧的 localStorage / BroadcastChannel **跨进程无效**。
- 每个进程自己的 `bridgeSem`（32）也互不相认。
- 被控看到的是两倍（或更多）直连 TCP。

这是「限制 (来源桥, 目标 IP) 并发」才覆盖得住的场景；单靠页面提示不够。

## 现有能力（已落地，但不管连接数）

可选独占控制权，**默认关**：

```bash
./rustdesk-web-v2-direct --listen :8081 --control
# 可选：--control-auto-approve
```

要点（细节以 `deploy/v2/controlroom/README.md` 为准）：

- 第一个连上的 web 客户端当控制者，后来者观看，申请后由当前控制者批准。
- 房间键是被控 **IP**（`NormalizeTarget`：`192.168.1.50` 与 `192.168.1.50:21118` 同一间）。
- `/control` 挂在与页面相同的 `--listen` 上（直连默认 `:8081`），**不开 8099**。
- 不改 hbbs/hbbr、不改被控 `src/server/`；原生客户端不进房间。
- **不限制** `/direct` 条数，也不限制被控上的 TCP 数。

另外，桥上已有进程级并发上限：`bridgeSem` 容量 32（`deploy/v2/web-direct/server/main.go`）。那是防止未认证会话耗尽内存/goroutine，**不是**「同一被控最多 N 路会话」。打满时返回 `503 too many connections`，与目标 IP 无关。

## 分层方案（提案，未实施）

以后若做，按层拆，不要混成一个「短时间连太多次就踢」。

### A. 并发会话上限（管误开，不管重连）

1. **浏览器（优先、成本低）**  
   同一源、同一目标 IP：用 `localStorage` + `BroadcastChannel` 标出「当前活跃控制页」。第二页打开同一 IP 时提示「已有一页在连」，而不是静默再开一条视频桥。  
   只覆盖 **同一浏览器 profile**。不能管情况 5。

2. **桥（可选硬帽）**  
   按 `(来源, 目标 IP)` 限制同时存在的桥，例如 2–3。给刷新/短暂双连留一点余量，避免 1 把合法 replace 误杀。  
   「来源」至少要能区分：同一 `--listen` 进程内的多路 `/direct`，以及（若以后要管情况 5）不同桥进程——后者需要被控侧或共享状态，本 fork 现在没有。

房间（`--control`）继续只管键鼠，不管这条上限。

### B. 重连冷却（管风暴，不要封禁）

- **客户端**：指数退避（断线后再连，而不是立刻 `start(id)`）。现有 `reconnect()` 没有退避。
- **桥**：同一目标上新 `/direct` 进来时，**串行替换**：先拆旧 TCP，再拨新的；不要让新旧两条并行到旧连接清干净为止。
- **不要**按「N 秒内连了 M 次」拒绝连接。

### C. 继续推荐可选 `--control`

有意多开时打开房间，而不是靠全局速率限制。缺省保持关，避免改变现网。

### D. 避免被控侧短间隔连接次数封禁

在被控 RustDesk 上按时间窗数连接并拒绝，调试成本高（尤其锁屏、UAC、会话断开后的重连），也和直连「谁都能连」的现行为冲突。本文不建议从那一层开刀。

### E. 可观测性

桥日志至少打出：

- 新的 `/direct`（现已有 `direct bridge <remote> <-> <addr>`）
- 目标 IP（规范化后与房间键一致更好）
- 是否在 replace 旧桥
- 该目标当前并发桥数（以及全局 `bridgeSem` 用量）

没有这些，很难区分情况 1 / 2 / 4。

## 以后若实施：建议顺序

1. **先做 B + 浏览器「单活跃页」提示**（A 的页面部分）。误伤小，能分开「双开」和「重连」。
2. **再考虑桥上的硬并发帽**（A 的桥部分，2–3 路 / 目标）。
3. **不要从「短间隔连接次数封禁」开始**（被控或桥上按时间窗拒绝）。
4. 协作场景继续走可选 `--control`，不要用全局 rate limit 替代房间。
